# 왕열 작가 홈페이지 개발시스템.md

## 문서 목표

이 문서는 왕열 작가 홈페이지 개선 과정을 처음부터 다시 진행해야 하는 초보자도 그대로 따라 할 수 있도록 정리한 실행 가이드다.

핵심 목표는 다음과 같다.

- 현재 사이트를 무작정 수정하지 않는다.
- 먼저 사이트의 의도와 디자인 기준을 문서로 고정한다.
- Lazyweb으로 실제 디자인 레퍼런스를 조사한다.
- getdesign.md로 DESIGN.md 문서 작성 방식을 참고한다.
- 최종적으로 왕열 작가 사이트 전용 DESIGN.md를 만든다.
- 그 기준에 따라 코딩 에이전시가 단계별로 사이트를 수정한다.

이 문서에서 가장 중요한 원칙은 다음이다.

> 코드 수정은 마지막이다.  
> 먼저 의도, 레퍼런스, 디자인 기준서를 확정한 뒤 구현한다.

---

# 1. 전체 역할 정의

## 1.1 사용자 역할

사용자는 최종 결정자다.

사용자가 해야 할 일은 다음이다.

- 사이트의 방향을 결정한다.
- 코딩 에이전시의 보고를 확인한다.
- 후보 디자인 중 어떤 방향이 맞는지 판단한다.
- 구현을 승인하거나 중단한다.

사용자는 직접 코딩하지 않아도 된다.

---

## 1.2 코딩 에이전시 역할

코딩 에이전시는 실행자다.

코딩 에이전시가 해야 할 일은 다음이다.

- GitHub 프로젝트를 열고 상태를 확인한다.
- Lazyweb을 연결하고 레퍼런스를 조사한다.
- getdesign.md에서 참고 후보를 조사한다.
- 문서를 생성하거나 보강한다.
- 사용자의 승인 후 코드 수정한다.
- 수정 후 결과와 리스크를 보고한다.

중요한 원칙:

> 코딩 에이전시는 사용자 승인 없이 코드를 수정하지 않는다.

---

## 1.3 감독관 역할

감독관은 지시자이자 검수자다.

감독관의 역할은 다음이다.

- 지금 무엇을 해야 하는지 정리한다.
- 코딩 에이전시에게 줄 지시문을 만든다.
- 코딩 에이전시의 보고를 평가한다.
- 다음 단계로 넘어가도 되는지 판단한다.
- 사용자가 초보자여도 길을 잃지 않게 순서를 고정한다.

---

# 2. 왕열 사이트의 최종 방향

## 2.1 사이트 정체성

왕열 작가 홈페이지는 단순한 작가 소개 랜딩페이지가 아니다.

목표는 다음이다.

> 왕열 작가의 작품을 조용하고 품격 있게 감상할 수 있는 온라인 미술관형 작가 아카이브

---

## 2.2 핵심 디자인 방향

사이트는 다음 분위기를 가져야 한다.

- 작품 중심
- 조용한 미술관
- 작가 아카이브
- 따뜻한 여백
- 절제된 타이포그래피
- 낮은 채도의 색상
- 한국적 현대성
- AI 디자인 느낌 제거

---

## 2.3 피해야 할 방향

다음 스타일은 피한다.

- AI SaaS 랜딩페이지 느낌
- 과한 그라데이션
- 글래스모피즘
- 둥근 카드 남발
- 쇼핑몰형 작품 카드
- 대시보드 UI
- 가격표/상품 리스트 느낌
- 과한 애니메이션
- 작품보다 UI가 튀는 디자인

---

# 3. 전체 개발 흐름

왕열 사이트 개선은 아래 순서로 진행한다.

```text
1. 현재 사이트 분석
2. 방안.md 작성
3. DESIGN.md 초안 작성
4. Lazyweb 연결
5. Lazyweb으로 레퍼런스 조사
6. lazyweb-reference.md 작성
7. getdesign.md 참고 후보 조사
8. DESIGN.md 보강
9. 1차 구현 계획 작성
10. 사용자 승인
11. 1차 코드 수정
12. 결과 검수
13. 2차 고도화
```

중요:

```text
1~8번은 문서와 조사 단계다.
9번 이후부터 구현 준비다.
11번에서 처음으로 코드 수정이 시작된다.
```

# 4. 현재까지 진행된 과정

## 4.1 현재 사이트 분석 완료

현재 사이트를 분석한 결과 다음 문제가 있었다.

- 작가 소개 랜딩페이지 느낌이 강하다.
- 작품 감상 중심의 온라인 미술관 느낌이 약하다.
- AI가 만든 듯한 일반적인 문장과 구조가 일부 있다.
- 공개 화면에 관리자/로딩/미완성 문구가 노출될 위험이 있다.
- 작품보다 설명과 이력이 먼저 보이는 구조다.

개선 방향은 다음으로 정리했다.

```text
작품 중심
온라인 미술관
작가 아카이브
조용한 고급감
AI 디자인 느낌 제거
```

---

## 4.2 방안.md 작성 완료

`방안.md`는 전략 문서다.

역할:

- 왜 사이트를 바꾸는지 설명
- 어떤 사이트가 되어야 하는지 정의
- 현재 사이트 문제 정리
- 개선 방향 제안
- 코딩 에이전시에게 전달할 큰 방향 정리

포함된 내용:

- 현재 사이트 분석
- 사이트 identity 정의
- 개선 아이디어
- UI 방향
- 작품 전시 구조
- 개발 지시 방향

---

## 4.3 DESIGN.md 초안 생성

`docs/DESIGN.md`는 디자인 기준서다.

역할:

- 코딩 에이전시가 디자인을 자기 마음대로 해석하지 못하게 한다.
- 색상, 폰트, 여백, 레이아웃, 금지 패턴을 고정한다.
- 왕열 작가 사이트의 디자인 헌법 역할을 한다.

초안에는 다음 내용이 들어가야 한다.

- 사이트 정체성
- 디자인 무드
- 색상 방향
- 타이포그래피 방향
- 레이아웃 원칙
- 금지 패턴

---

## 4.4 Lazyweb 연결 완료

Lazyweb은 디자인 레퍼런스 조사 도구다.

사용 목적:

- 실제 미술관 사이트 참고
- 갤러리 사이트 참고
- 작가 포트폴리오 참고
- 작품 상세 페이지 참고
- 전시 아카이브 참고
- 에디토리얼 레이아웃 참고

코딩 에이전시가 완료한 내용:

- 토큰을 홈 디렉터리 로컬 파일에 저장
- Codex marketplace에 lazyweb 소스 추가
- `~/.codex/config.toml`에서 lazyweb 활성화
- 프로젝트 저장소에는 설정 파일을 만들지 않음
- 프로젝트 코드 수정 없음
- `lazyweb_health` 호출 성공
- `lazyweb_search` 호출 성공

확인된 Lazyweb 도구:

```text
lazyweb_health
lazyweb_search
lazyweb_find_similar
lazyweb_compare_image
lazyweb_list_categories
lazyweb_list_collections
```

판단:

> Lazyweb 연결은 성공했다.

---

## 4.5 lazyweb-reference.md 생성 완료

`docs/lazyweb-reference.md`는 Lazyweb 조사 결과 문서다.

역할:

- 실제 사이트 레퍼런스 조사 결과 기록
- Hero, 갤러리, 작품 상세, 전시 아카이브 방향 정리
- 무엇을 참고하고 무엇을 피해야 하는지 고정

---

## 4.6 getdesign.md 참고 후보 조사 완료

getdesign.md는 디자인을 그대로 베끼기 위한 도구가 아니라, `DESIGN.md` 같은 디자인 기준 문서를 어떻게 구조화하고 서술하는지 참고하기 위한 도구다.

이번 프로젝트에서 참고한 후보는 다음 세 가지다.

- WIRED
- Ferrari
- Sanity

각 후보에서 가져온 것은 다음뿐이다.

- WIRED: 에디토리얼 정보 위계와 도록형 문서 구조
- Ferrari: 럭셔리 무드 정의 방식과 이미지 위계 설명 방식
- Sanity: content-first 구조와 아카이브형 정보 정리 방식

가져오지 않는 것:

- 브랜드 색상
- 서비스 UI
- 과한 시네마틱 연출
- 제품 마케팅 톤

판단:

> getdesign.md는 왕열 사이트의 시각 스타일 복제용이 아니라, 문서화 방식 참고용이다.

---

## 4.7 DESIGN.md 보강 완료

`docs/DESIGN.md`는 초안 단계에서 끝나는 문서가 아니다.

Lazyweb 조사 결과와 getdesign.md 참고 방식을 반영해, 실제 구현 전에 충분히 구체적인 디자인 기준서로 보강해야 한다.

최종적으로 포함되어야 하는 항목은 다음과 같다.

- Identity / Role
- Mood / Tone
- Content Priority
- Color Tokens
- Typography Rules
- Spacing System
- Imagery Rules
- Layout Rules
- Hero Rules
- Works Gallery Rules
- Artwork Detail Rules
- Artist / Exhibitions / Contact Rules
- Motion Rules
- Mobile Rules
- Forbidden Patterns
- Acceptance Checklist

판단:

> DESIGN.md는 구현자가 자기 취향으로 해석하지 못하게 막는 기준서다.

---

## 4.8 IMPLEMENTATION_CHECKLIST 작성 완료

`docs/IMPLEMENTATION_CHECKLIST.md`는 실제 코딩에 들어가기 전 마지막 준비 문서다.

역할:

- DESIGN.md 기준을 실제 수정 순서로 번역
- 구현 범위를 Phase 단위로 분리
- 수정 대상 예상 파일 정리
- 금지 작업과 검수 기준 고정
- 롤백 기준 명확화

핵심 원칙:

- 코드 수정은 한 번에 전체를 뒤엎지 않는다.
- Phase 1, Phase 2, Phase 3로 나눈다.
- 각 단계는 독립적으로 검수 가능해야 한다.
- 문서에서 승인된 범위만 구현한다.

Phase 구성:

- Phase 1: 공개 화면 문제 제거 + 작품 우선 구조 복원
- Phase 2: 작품 상세 감상 경험 개선
- Phase 3: Artist / Exhibitions / Contact / 반응형 최종 정리

판단:

> IMPLEMENTATION_CHECKLIST.md는 “무엇을 먼저 고치고, 무엇을 나중에 고칠지”를 고정하는 실행 문서다.

# 8. 최종 원칙 요약

왕열 사이트 개선에서 가장 중요한 원칙은 다음이다.

- 작품이 먼저다.
- 디자인은 조용해야 한다.
- 문서는 구현보다 먼저다.
- 구현은 Phase 단위다.
- 승인 없는 코드 수정은 금지다.

최종 목표는 다음 한 문장으로 정리된다.

> 왕열 작가의 작품을 가장 우선에 두는 조용한 온라인 미술관형 작가 홈페이지를 만든다.
- 참고할 패턴 정리
- 피해야 할 패턴 정리
- Hero, Works, Artwork Detail, Mobile 개선 방향 정리
- DESIGN.md에 반영할 항목 정리

이 문서는 직접 구현 지시서가 아니다.

이 문서는 DESIGN.md를 보강하기 위한 참고 자료다.

## 4.6 getdesign.md 활용 방식 확인 완료

getdesign.md는 Lazyweb처럼 연결해서 쓰는 도구가 아니다.

정확한 역할:

```text
Lazyweb = 실제 사이트 화면 레퍼런스 조사
getdesign.md = DESIGN.md 문서 작성 방식 참고
```

getdesign.md에서 가져올 것은 디자인 자체가 아니다.

가져올 것:

- 문서 구조
- 색상 규칙 작성 방식
- 타이포그래피 규칙 작성 방식
- 레이아웃 규칙 작성 방식
- 금지 패턴 정리 방식
- 적용 대상과 비적용 대상을 나누는 방식

가져오면 안 되는 것:

- 특정 브랜드 색상
- 브랜드 로고 느낌
- SaaS CTA 구조
- 대시보드 UI
- 가격 페이지 느낌
- 테크 스타트업 분위기

---

## 4.7 getdesign.md 참고 후보 조사 완료

코딩 에이전시가 getdesign.md에서 참고 후보 3개를 조사했다.

선정 후보:

1. WIRED
2. Ferrari
3. Sanity

각 후보의 역할:

### WIRED

참고할 것:

- 에디토리얼 정보 위계
- 도록형 문서 구조
- 제목/본문/보조 텍스트 계층

가져오면 안 되는 것:

- 뉴스 사이트식 정보 과밀
- 기사 타일 구조
- 강한 링크 색상

---

### Ferrari

참고할 것:

- 럭셔리 무드 정의 방식
- 이미지 위계 설명 방식
- 짧고 강한 무드 문장

가져오면 안 되는 것:

- 과한 블랙
- 강한 레드
- 자동차 광고식 시네마틱 연출
- 남성적 과장

---

### Sanity

참고할 것:

- content-first 구조
- 아카이브형 정보 정리 방식
- 섹션별 문서화 방식

가져오면 안 되는 것:

- CMS 제품 톤
- 서비스형 UI
- 다크 에디토리얼 편향

---

# 8. 구현 승인 후 코드 수정

1차 구현 계획을 보고받은 뒤 사용자가 승인하면 그때 코드 수정한다.

구현 시 원칙:

- 작은 범위만 수정한다.
- 문서 기준에서 벗어나지 않는다.
- UI가 작품보다 튀면 실패로 본다.
- 수정 후 반드시 Git 상태를 보고한다.
- 수정 후 사용자가 확인할 수 있는 결과를 제공한다.

```text
8. DESIGN.md 금지 패턴을 위반하지 않았는가?
```

필요하면 Lazyweb으로 재평가한다.

# 11. 초보자를 위한 핵심 주의사항

## 11.1 바로 코드 수정하지 말 것

가장 흔한 실수는 문서 없이 바로 수정하는 것이다.

잘못된 흐름:

```text
사이트가 별로다
→ 바로 디자인 수정
→ 방향이 흔들림
→ AI 느낌 심해짐
```

올바른 흐름:

```text
사이트가 별로다
→ 방안.md 작성
→ Lazyweb 조사
→ getdesign 참고
→ DESIGN.md 확정
→ 구현 계획
→ 승인 후 코드 수정
```

---

## 11.2 레퍼런스를 그대로 베끼지 말 것

Lazyweb과 getdesign은 참고 자료다.

그대로 적용하면 왕열 사이트의 정체성이 사라진다.

원칙:

```text
레퍼런스에서 구조를 가져온다.
브랜드 느낌은 가져오지 않는다.
```

---

## 11.3 코딩 에이전시에게 항상 “수정하지 말라”를 먼저 말할 것

조사 단계와 계획 단계에서는 반드시 아래 문장을 넣는다.

```text
아직 사이트 코드는 수정하지 마라.
```

이 문장을 빼면 코딩 에이전시가 바로 코드를 수정할 수 있다.

---

## 11.4 보고 형식을 고정할 것

보고 형식을 고정하면 검수가 쉬워진다.

예:

```text
1. 한 일
2. 수정한 파일
3. 수정하지 않은 파일
4. 리스크
5. 다음 단계
```

# 14. 이 문서의 사용법

다음에 같은 과정을 다시 진행할 때는 이 순서대로 하면 된다.

1. 먼저 이 문서를 읽는다.
2. 현재 단계가 어디인지 확인한다.
3. 해당 단계의 지시문만 코딩 에이전시에게 전달한다.
4. 코딩 에이전시의 보고를 받는다.
5. 보고가 맞으면 다음 단계로 넘어간다.
6. 보고가 이상하면 코드 수정 전에 중단한다.

이 방식으로 진행하면 초보자도 큰 실수 없이 AI 코딩 에이전시를 감독할 수 있다.
